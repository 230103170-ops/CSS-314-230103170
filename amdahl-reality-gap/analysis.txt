Q1. What parallel fraction does Amdahl's Law predict?

Using the two-thread measurement:

T_2 = 0.794056 s

S_2 = T_seq / T_2
S_2 = 1.4786675 / 0.794056
S_2 = 1.8622

Amdahl's Law is:

S(k) = 1 / ((1 - p) + p/k)

Using k = 2 and S_2 = 1.8622, the estimated parallel fraction is:

p = 0.9260

Therefore, approximately 92.60% of the workload is parallelizable and
approximately 7.40% behaves as the serial fraction according to this fit.


Q2. How does measured scaling compare with Amdahl's prediction?

The measured OpenMP results were:

Using T_seq = 1.4786675 s, the approximate measured speedups were:

1 thread:  0.997x
2 threads: 1.862x
4 threads: 3.280x
8 threads: 5.394x
10 threads: 6.176x

The measured speedup increases strongly up to the physical core count, but
it does not continue to scale linearly. The 16-thread result is almost the
same as the 10-thread result because this machine has only 10 physical and
10 logical CPU cores.

The Amdahl model is an idealized prediction based mainly on the fitted
parallel fraction. Real execution also includes OpenMP overhead, thread
management, scheduling, load imbalance, cache effects, and the heterogeneous
4-performance-core plus 6-efficiency-core architecture. These effects create
a reality gap between the theoretical model and measured performance.


Q3. What was the effect of false sharing?

The false-sharing experiment used 10 threads.

Adjacent counters:
0.297862 s

Padded counters:
0.137113 s

False-sharing / padded ratio:
2.172x

Both versions produced the same checksum of 1,317,000,000, so they performed
equivalent logical work.

The adjacent-counter version was approximately 2.17 times slower than the
padded version in this experiment. Padding separates per-thread counters in
memory and reduces cache-line contention between threads. The measurement
therefore demonstrates a significant performance penalty associated with
false sharing for this benchmark.


Q4. How did OpenMP scheduling affect performance?

The scheduling experiment used 10 threads and produced these results:

static:          0.234338 s
static,1000:     0.218408 s
dynamic,100:     0.219916 s
dynamic,10000:   0.227578 s
guided:          0.214514 s

All scheduling variants produced max_steps = 688 and checksum = 82,237,874,
confirming equivalent computational results.

Guided scheduling was the fastest measured strategy at 0.214514 seconds.
It was approximately 8.5% faster than the default static result in this run.

Collatz iterations have variable execution costs because different starting
values require different numbers of steps. Therefore, an adaptive scheduling
strategy can improve load balance. In this measurement, guided scheduling
provided the best balance between scheduling overhead and workload
distribution.


Conclusion

The experiment demonstrated that parallel execution substantially reduced
the Collatz workload runtime on the Apple M4. The fitted parallel fraction
was approximately 92.60%. The best measured scaling result was approximately
6.20x at 16 OpenMP threads, although performance had already nearly plateaued
at the machine's 10-core hardware limit.

The experiments also showed that practical multicore performance depends on
more than the theoretical parallel fraction. Cache-line contention, scheduling
policy, OpenMP overhead, load imbalance, and hardware core characteristics
all contribute to the gap between ideal Amdahl scaling and real performance.
